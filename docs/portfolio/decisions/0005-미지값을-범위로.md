# ADR 0005 — 사용자가 모르는 값은 범위로 계산한다

- **상태**: 채택
- **일자**: 2026-09-02
- **관련**: [Phase 1 설계 스펙](../../superpowers/specs/2026-08-28-phase1-calculator-ui-design.md), [TS 0004](../troubleshooting/0004-과세대상-음수-클램프.md)

## 맥락

Phase 0에서 만든 계산 엔진 `calculateWithdrawal` 은 입력 13개를 **전부** 요구한다.
그중 사용자가 실제로 아는 것은 절반이 안 된다.

특히 **재원 구분**이 문제다. 연금계좌 잔액은 법적으로 세 갈래로 나뉘고
(과세제외금액 / 이연퇴직소득 / 세액공제분+운용수익), 어느 재원이냐에 따라 세율이
0% ~ 29%까지 벌어진다. 그런데 자기 계좌에서 얼마가 어느 재원인지 아는 사람은 드물다.

계산기를 쓰려면 모르는 값을 채워야 하고, 모르는 값을 채우려면 계산기를 못 쓴다.

## 검토한 선택지

**① 모르면 못 쓰게 한다 (전부 필수 입력)**
정확하다. 그리고 아무도 안 쓴다. 첫 화면에서 13개를 묻는 계산기는 이탈률이 곧 100%다.

**② 그럴듯한 기본값으로 채운다**
"과세제외금액은 보통 0이니까 0", "근속연수는 보통 20년이니까 20".
쓰기는 쉬운데 **결과가 거짓말이 된다.** 사용자는 자기가 입력하지 않은 값이
결과를 얼마나 흔들었는지 알 수 없다. 세금 계산기에서 이건 치명적이다.

**③ 모르는 값의 경계를 잡아 범위로 답한다**
"세금은 12만 원에서 303만 원 사이입니다. 근속연수를 알려주시면 좁혀집니다."
정직하지만 첫인상이 나쁘다. 범위가 넓으면 계산기로 보이지 않는다.

## 결정

**③을 택하되, 범위를 예외 경로로 만든다.**

`src/lib/tax/range.ts` 에 래퍼를 얹는다. 기존 `calculateWithdrawal` 은 손대지 않는다.

```ts
calculateWithdrawalRange(input, year) → {
  certain,          // 세금이 확정됐는가 (min.totalTax === max.totalTax)
  min, max,         // 미지 필드 경계값 조합 중 세금이 가장 작은/큰 결과
  representative,   // 화면 대표값 = max
  assumptions,      // 대신 세운 전제 (화면 문구를 그대로 만든다)
  missing,          // 아직 안 답한 값 (후속 질문을 그대로 만든다)
}
```

여기에 네 가지 판단이 들어 있다.

**(가) 퇴직금 수령 여부는 "모르겠어요"를 허용하지 않는다**

`severance: PartialSeverance | null` — 타입 수준에서 `'unknown'` 을 못 넣는다.
"퇴직금을 이 계좌로 받으셨나요?"는 누구나 즉답할 수 있고, 이 답 하나로 불확실성 대부분이 사라진다.
받았다고 답한 뒤 **금액·근속연수를 모르는 것**은 허용한다.

**(나) 대표값은 `max`(가장 불리한 쪽)로 둔다**

세금 계산기에서 낙관적 값을 보여주면 실제 납부 시 "더 나왔다"가 된다.
반대 방향 오차가 안전하다.

**(다) 경계값은 이론적 극단이 아니라 현실적 양 끝으로 잡는다**

| 미지 필드 | 경계 | 근거 |
|---|---|---|
| 퇴직급여액 | 0 ~ (총잔액 − 과세제외금액) | 잔액을 넘을 수 없다 |
| 근속연수 | 1년 ~ (나이 − 18)년 | 근로 가능 최소 연령. 길수록 퇴직소득세가 낮다 |
| 타 소득 | 0 ~ 최고세율 구간 | 아래 설명 |
| 과세제외금액 | **범위 없음. 0으로 가정** | 세액공제 한도 초과 납입이 있어야만 생긴다 |

과세제외금액을 범위로 열지 않은 것이 핵심이다. 이론적으로는 잔액 전부가 비과세일 수도 있지만
실제로 그런 사람은 거의 없다. 열면 폭만 무의미하게 넓어진다. 대신 **가정을 명시**하고
고급 항목에서 직접 입력할 수 있게 둔다.

**(라) 건보 판정은 값이 없으면 아예 생략한다**

건강보험 자격·재산세 과세표준·타 소득 중 하나라도 모르면 피부양자 판정 결과를 지우고
"몰라서 생략했습니다 + 위택스에서 확인하세요"를 남긴다. 추측한 판정을 보여주지 않는다.

## 근거 — 타 소득의 상한을 "최고세율 구간"으로 잡은 이유

이게 가장 설명이 필요한 부분이다.

연 1,500만 원을 넘는 사적연금은 **종합과세와 16.5% 분리과세 중 유리한 쪽**으로 과세된다.
종합과세액은 타 소득이 많을수록 커진다. 즉 세액은 다음과 같다.

```
세액 = min(종합과세액(타 소득), 16.5% 분리과세액)
```

타 소득이 아무리 커져도 **세액은 16.5%를 넘지 못한다.** 상한이 이미 존재한다.
그래서 "최고세율 구간의 타 소득"을 넣으면 그 상한값이 그대로 나온다.
넣는 숫자는 극단이지만 **나오는 범위는 극단이 아니다.** 실제 세액 상한 그 자체다.

이 값은 세액 상한을 끌어내는 수단일 뿐이고, 건보 판정은 (라)에 따라 생략되므로
황당한 소득 금액이 화면 문구로 새어나가지 않는다.

## 결과

테스트 31개를 새로 붙였다 (전체 61개). 스펙이 요구한 성질 네 가지를 전부 테스트로 고정했다.

| 성질 | 확인 방법 |
|---|---|
| 답을 추가하면 폭은 넓어지지 않는다 | 근속연수 → 금액 순으로 답하며 폭 단조 감소 확인 |
| `certain` 이면 min·max·representative가 같다 | 세 값 deep equal |
| 미지 필드가 있으면 가정이 비지 않는다 | `assumptions` 에 필드명·이유·확인 방법 존재 |
| 확정 입력은 기존 엔진과 결과가 완전히 일치한다 | `calculateWithdrawal` 결과와 deep equal |

마지막 성질이 회귀 안전망이다. 래퍼가 기존 엔진 동작을 바꾸면 즉시 깨진다.

실제 값 (63세 · 잔액 2.5억 · 인출 1,500만):

| 답한 정도 | 결과 |
|---|---|
| 퇴직금 없음 | **83만 원 확정** |
| 퇴직금 8,000만·20년 | **9만 원 확정** |
| 퇴직금 받았는데 금액·근속연수 모름 | 12만 ~ 303만 원 |

## 감수한 것

**아무것도 모르는 경우의 폭이 25배로 벌어진다.**

상한 303만 원은 "퇴직금 2.5억을 근속 1년에 받았다"는 조합에서 나온다.
산수는 맞다(퇴직소득세 실효세율 28.9%). 하지만 현실에 거의 없는 모서리다.
스펙 §4.2가 경계했던 "폭만 무의미하게 넓어지는" 상황에 이 조합만은 걸린다.

근속연수 하나만 답하면 폭이 무너지고, 애초에 "퇴직금은 받았는데 금액도 근속연수도 모른다"는
드문 경로이므로 그대로 뒀다. **경계를 좁히려면 금액과 근속연수 사이에 상관관계를 가정해야 하는데,
그건 (나)에서 거부한 "그럴듯한 기본값"과 같은 것이다.**

## 되돌리는 비용

**낮다.** `range.ts` 는 기존 엔진 위에 얹힌 순수 함수 한 개이고, 엔진을 수정하지 않았다.
파일을 지우고 화면에서 `calculateWithdrawal` 을 직접 부르면 끝난다.

다만 그 순간 "13개 전부 입력" 화면으로 돌아가야 한다. 되돌리는 비용이 낮은 것은 코드 쪽이고,
제품 쪽은 그렇지 않다.
