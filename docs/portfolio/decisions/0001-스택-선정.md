# ADR 0001 — 스택 선정

- **상태**: 채택
- **일자**: 2026-08-28
- **관련**: [ADR 0002](0002-계산은-브라우저에서.md)

## 맥락

만들려는 것은 **불특정 다수가 쓰는 공개 웹 계산기**다. 이 조건에서 세 가지 제약이 나온다.

1. **개인정보** — 나이·소득·재산을 입력받는다. 서버로 보내는 순간 개인정보처리방침·보관·유출 책임이 생긴다.
2. **검색 유입** — "퇴직연금 인출 세금" 같은 키워드로 들어오는 서비스다. SEO가 안 되면 사용자가 없다.
3. **운영 비용** — 수익이 없는 초기에 서버를 상시 띄워둘 이유가 없다.

내 주력은 Java/JSP다. 익숙함만 따지면 Spring Boot가 편하다.

## 검토한 선택지

| 안 | 장점 | 문제 |
|---|---|---|
| **Spring Boot + Thymeleaf** | 내가 가장 익숙함 | 서버 상시 운영(비용), 입력값이 서버로 감, SEO 불리 |
| **순수 HTML + JS** | 학습 비용 0, 즉시 시작 | 다년도 시뮬레이션(30년 표 + 차트 + 슬라이더)에서 DOM 조작 코드가 감당 안 됨 |
| **Next.js + TypeScript** | 정적 생성으로 SEO 확보, 무료 배포, 클라이언트 계산 | React 학습 비용 |

## 결정

**Next.js + TypeScript**를 쓴다.

## 근거

익숙함이 아니라 **제약 조건**이 골랐다.

- 계산을 브라우저에서 끝내면 제약 1이 해결되는데, 그러면서도 SEO(제약 2)를 포기하지 않는 방법이 정적 생성이다. 이 둘을 동시에 만족하는 게 Next.js였다.
- 순수 HTML+JS도 Phase 1까지는 충분하다. 하지만 이 서비스의 차별점은 **다년도 시뮬레이션**이고, 거기서는 값이 바뀔 때마다 30년치 표와 차트를 다시 그려야 한다. `innerHTML`로 밀어넣는 방식은 그 지점에서 무너진다. **어차피 갈아엎을 거면 처음부터 하는 게 싸다.**
- Spring Boot를 포기한 게 아깝지 않은 이유: 서버가 필요해지는 시점(회원·저장)이 Phase 4다. 그때 Next.js의 Route Handler로 붙이면 되고, 정 안 되면 그때 Java 백엔드를 분리하면 된다. **지금 결정할 필요가 없는 것을 지금 결정하지 않는다.**

## 결과

- Next.js 16.3.3 / React 19.2.8 / TypeScript 5 / Tailwind CSS 4
- 테스트는 Vitest
- **`output: 'export'`(완전 정적 export)는 켜지 않는다.** 켜면 서버 기능이 사라져 Phase 4에서 되돌려야 한다. 지금 켜서 얻는 것도 없다.

## 되돌리는 비용

계산 엔진(`src/lib/tax/`)은 React를 import하지 않는 순수 TypeScript다.
스택을 갈아엎어도 **엔진은 그대로 옮겨간다.** 버려지는 건 화면 코드뿐이다.
이 프로젝트에서 가치 있는 건 화면이 아니라 엔진이므로, 스택 결정의 리스크는 낮다.
