# ADR 0006 — 화면 상태를 엔진 입력 타입 그대로 쓴다

- **상태**: 채택
- **일자**: 2026-09-02
- **관련**: [ADR 0005](0005-미지값을-범위로.md), [Phase 1 설계 스펙 §5.3](../../superpowers/specs/2026-08-28-phase1-calculator-ui-design.md)

## 맥락

계산기 화면은 입력을 모아 엔진에 넘긴다. 보통은 이렇게 만든다.

```
FormState (화면용)  →  변환 함수  →  PartialWithdrawalInput (엔진용)
```

화면은 만원 단위·문자열·"모름 체크박스"를 다루고 엔진은 원 단위 숫자를 다루니
중간에 변환 계층을 두는 게 자연스러워 보인다.

## 결정

**변환 계층을 만들지 않는다. 화면 상태가 곧 엔진 입력이다.**

```ts
export type FormState = PartialWithdrawalInput & {
  severanceAnswered: boolean
}
```

`calculateWithdrawalRange(form)` 을 그대로 호출한다.

만원↔원 변환은 상태가 아니라 **입력 컴포넌트 한 곳**(`ManInput`)에 가둔다.
`ManInput` 은 만원으로 보여주고 원으로 내보낸다. 상태에는 언제나 원만 들어간다.

## 근거

변환 계층은 **틀릴 수 있는 코드가 한 겹 더 생기는 것**이다.
이 프로젝트에서 틀리면 세금 숫자가 틀린다.

엔진은 이미 "모름"을 1급 개념으로 갖고 있다(`Maybe<T> = T | 'unknown'`).
화면이 별도 표현을 만들어 다시 매핑할 이유가 없다. 엔진 타입이 바뀌면 화면이 컴파일에서 깨진다.
그게 맞는 동작이다.

## 예외 하나 — `severanceAnswered`

엔진의 `severance: PartialSeverance | null` 에서 `null` 은 **"퇴직금을 안 받았다"는 답**이다.
"아직 안 물어봤다"는 상태가 아니다. 엔진 타입에는 후자가 없다. 있을 이유도 없다.

답하기 전에 `null` 로 두면 안 받은 것으로 계산해 버린다.
[ADR 0005](0005-미지값을-범위로.md)가 거부한 "그럴듯한 기본값"과 같은 잘못이다.

그래서 UI 전용 불리언 하나를 얹었다. 이 값은 엔진으로 넘어가지만 무시된다.

## `certain` 의 정의 — 스펙 해석

스펙은 `certain: boolean // true면 min === max` 라고만 적어 뒀다. 두 가지로 읽힌다.

| 해석 | 결과 |
|---|---|
| ① 모든 입력이 채워졌다 | 1단계만 답한 사람은 항상 `false` |
| ② 세금이 확정됐다 (`min.totalTax === max.totalTax`) | 건보 입력이 비어도 `true` 가능 |

**②를 택했다.** 스펙 §3.1이 "대부분의 사용자는 1단계에서 이미 단일 값을 받는다"고 했는데,
1단계에서는 건강보험 자격·재산세 과세표준·타 소득 세 칸이 비어 있다.
①로 읽으면 그 문장이 성립할 수 없다.

건보 판정의 불확실성은 `certain` 이 아니라 `missing` 과 "판정 생략" 문구로 따로 표현한다.

## 감수한 것

**`FormState` 에 엔진이 쓰지 않는 필드가 섞인다.** 타입만 보고는 어디까지가 엔진 계약인지
바로 알기 어렵다. 주석으로 막아 뒀지만 주석은 강제력이 없다.

필드가 두세 개로 늘어나면 이 결정은 다시 봐야 한다. 지금은 하나뿐이라 변환 계층의 비용이 더 크다.

## 되돌리는 비용

**낮다.** `FormState` 를 독립 타입으로 떼고 `toEngineInput(form)` 을 만들면 된다.
변환 지점이 `Calculator.tsx` 한 곳뿐이라 손댈 파일이 하나다.
