# ADR 0002 — 세금 계산은 브라우저에서 한다

- **상태**: 채택
- **일자**: 2026-08-28
- **관련**: [ADR 0001](0001-스택-선정.md)

## 맥락

이 계산기는 사용자에게 다음을 입력받는다.

- 만 나이
- 공적연금 소득, 근로·사업·임대 소득, 금융소득
- 부동산 재산세 과세표준
- 연금계좌 잔액 (재원별)

**한 사람의 재산 상태가 거의 그대로 드러나는 조합이다.** 이름이 없을 뿐 민감정보에 가깝다.

일반적인 웹 서비스라면 이걸 서버로 POST 하고, 서버가 계산해서 결과를 내려준다.
그렇게 하면 계산 로직이 사용자에게 노출되지 않는다는 장점도 있다.

## 결정

**계산을 전부 브라우저에서 수행한다. 입력값은 서버로 전송하지 않는다.**

회원이 "이 시나리오를 저장" 을 **명시적으로 누를 때만** 데이터가 서버로 간다 (Phase 4).

## 근거

**① 안 받는 것이 가장 확실한 보호다**

수집하지 않은 데이터는 유출될 수 없다. 개인정보처리방침, 보관 기간 관리, 파기 절차, 접근 통제 —
데이터를 안 받으면 이 전부가 필요 없어진다. 1인 개발 프로젝트에서 이건 결정적이다.

**② 로직 은닉은 이 서비스에서 가치가 없다**

"계산 로직을 감춰야 한다"는 반론이 가능하다. 하지만 **이 계산의 근거는 전부 공개된 법령이다.**
숨길 것이 없고, 오히려 근거를 투명하게 밝히는 것이 신뢰를 만든다.
실제로 `docs/tax-rules-2026.md`에 모든 계산 근거를 조문 번호까지 공개하고 있다.

**③ 신뢰가 곧 기능이다**

세금 계산기에 재산 정보를 넣는 건 심리적 저항이 큰 행동이다.
**"입력하신 정보는 서버로 전송되지 않습니다"** 는 안내 문구가 아니라 **전환율을 올리는 기능**이다.
서버에서 계산하면 이 말을 할 수 없다.

## 결과

- 계산 엔진은 브라우저에서 실행된다
- 비회원은 어떤 요청도 서버로 보내지 않는다
- `AGENTS.md` 규칙 1에 명문화 — 서버 전송 설계를 제안하지 않는다

## 감수하는 것

- 계산 로직이 번들에 포함되어 누구나 읽을 수 있다 → **의도한 것이다** (근거 ②)
- 서버 로그로 사용 패턴을 분석할 수 없다 → 필요하면 입력값이 아닌 **익명 이벤트**만 별도로 수집한다
- 무거운 최적화 연산(Phase 2 다년도 시뮬레이션)도 브라우저에서 돌아야 한다
  → 실측 후 느리면 Web Worker로 옮긴다. 그래도 서버로 보내지는 않는다.
