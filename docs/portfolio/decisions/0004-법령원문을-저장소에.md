# ADR 0004 — 법령 조문 원문을 저장소에 보관한다

- **상태**: 채택
- **일자**: 2026-08-28
- **관련**: [ADR 0003](0003-세법규칙을-데이터로.md), [TS 0002](../troubleshooting/0002-법령원문-수집-파이프라인.md)

## 맥락

처음 세법 규칙 명세서를 쓸 때, 출처가 이랬다.

- 증권사 연금 안내 페이지
- 회계법인 뉴스레터
- 블로그 정리 글

전부 성실하게 쓰인 자료지만 **2차 자료**다. 그리고 실제로 이 중 하나가 개정 전 세율을 담고 있었고,
나는 그걸 그대로 코드에 넣었다 ([TS 0001](../troubleshooting/0001-종신연금-세율-오류.md)).

문제는 오류 자체보다 **"내가 틀렸다는 걸 발견할 방법이 없었다"** 는 점이다.
숫자의 출처가 블로그 링크뿐이면, 그 블로그가 갱신되거나 사라지면 근거가 증발한다.

## 결정

**법령 조문 원문을 텍스트로 내려받아 `docs/sources/` 에 저장소와 함께 버전 관리한다.**

- 근거로 인정하는 것: 법령 원문(법제처), 소관 기관 자료(국세청·국민건강보험공단)
- 근거로 인정하지 않는 것: 증권사·언론·블로그

각 파일은 헤더에 **공포일·공포번호·시행일·요청 URL·취득일**을 남긴다.

```
# 소득세법 제129조
# 공포 20251223 제21221호 / 시행 20260701
# 출처: 법제처 국가법령정보 공동활용 OPEN API
# https://www.law.go.kr/DRF/lawService.do?OC=<본인ID>&target=law&type=JSON&MST=280405&JO=012900
# 취득일: 2026-08-28
```

## 근거

**① 금융·세무 도메인은 "왜 이 숫자인가"에 답할 수 있어야 한다**

계산 결과가 틀렸다는 문의가 들어왔을 때, 근거 조문을 즉시 제시할 수 있어야 한다.
링크만 남기면 그 링크가 죽는 순간 답할 수 없다.

**② 개정 시 diff가 보인다**

원문을 저장소에 두면 다음 개정 때 스크립트를 다시 돌려 **`git diff` 로 무엇이 바뀌었는지**
바로 확인할 수 있다. 이게 이 방식의 가장 큰 실익이다.

**③ 링크는 썩고 파일은 남는다**

법제처 URL은 법령 일련번호(MST)를 포함하는데, 개정되면 번호가 바뀐다.
문서에 URL만 적어두면 1년 뒤엔 대부분 깨진다.

## 결과

`scripts/fetch-law.mjs` 로 수집을 자동화했다.

```bash
node scripts/fetch-law.mjs --law 소득세법 --jo 129 --save
node scripts/fetch-law.mjs --law "소득세법 시행령" --jo 40 --branch 3 --save
```

현재 보관 중인 조문 9건:

| 조문 | 내용 |
|---|---|
| 소득세법 §14 | 분리과세연금소득 (연 1,500만 원) |
| 소득세법 §47조의2 | 연금소득공제 |
| 소득세법 §48 | 퇴직소득공제 |
| 소득세법 §55 | 기본세율·퇴직소득 산출세액 |
| 소득세법 §64조의4 | 연금소득 세액계산 특례 (100분의 15) |
| 소득세법 §129 | 원천징수세율 |
| 시행령 §40조의2 | 연금수령한도·연금수령연차 |
| 시행령 §40조의3 | 연금계좌의 인출순서 |
| 시행령 §40조의4 | 연금계좌 이체 시 순서 |

## 감수하는 것

- 저장소에 법령 텍스트가 쌓인다 → 텍스트 파일이라 부담이 없고, 얻는 추적성이 훨씬 크다
- 수동으로 갱신해야 한다 → 개정은 연 1~2회다. 자동화할 만큼 잦지 않다.
- 별표·서식은 아직 미수집 (국민건강보험법 시행규칙 [별표 1의2]) → 별도 API가 있어 추후 추가
