# Phase 1 설계 — 입력 화면과 결과 리포트

- **작성일**: 2026-08-28
- **상태**: 승인됨
- **선행**: Phase 0 (계산 엔진, 세법 명세서, 테스트 30개)

---

## 1. 목표

계산 엔진에 물어볼 방법을 만든다.

현재 `src/app/page.tsx`는 값이 하드코딩된 검증용 페이지다. 입력 요소가 하나도 없다
(`<input>` 0개, `<form>` 0개, `'use client'` 없음). 엔진은 "만 63세가 2,500만 원을 인출하면
세금이 얼마인지"를 정확히 답할 수 있지만, **사용자가 그것을 물어볼 수단이 없다.**

Phase 1이 끝나면 다음이 가능해야 한다.

- 처음 방문한 사람이 자기 상황을 입력해 세금과 세후 실수령액을 확인한다
- 금액을 조절하며 세금이 어떻게 변하는지 직접 탐색한다
- 배포된 URL로 접속할 수 있다

## 2. 핵심 문제 — 사용자는 필요한 값을 대부분 모른다

엔진의 `WithdrawalInput`은 13개 값을 요구한다. 처음 방문한 사람이 아는 것은 절반이 안 된다.

특히 **재원 구분**(과세제외금액 / 이연퇴직소득 / 과세대상)은 세금을 가르는 핵심 변수인데,
자기 IRP 안에서 얼마가 어느 재원인지 아는 사람은 드물다.

### 2.1 발견 — 입력마다 무게가 다르다

코드를 확인한 결과, 모든 입력이 항상 필요한 것은 아니다.

- `otherIncome`은 `estimateComprehensiveTax` 안에서만 쓰이고, 그 함수는
  **`overCap.exceeded`일 때만** 호출된다 (`withdrawal.ts`)
- `propertyTaxBase`는 `assessHealthInsurance`에서만 쓰인다

따라서:

> **목표 인출액이 1,500만 원 이하이면 타 소득을 몰라도 세금은 정확히 계산된다.**
> **재산세 과세표준은 세금 계산에 전혀 쓰이지 않는다. 건강보험료 판정에만 쓰인다.**

### 2.2 입력 13개 분류

| 입력 | 사용자가 아는가 | 무엇에 영향 |
|---|---|---|
| 나이 | 안다 | 세율 |
| 목표 인출액 | 본인이 정한다 | 전부 |
| 근속연수 | 안다 | 퇴직소득세 |
| 퇴직급여액 | 받은 사람은 안다 | 퇴직소득세 |
| 건강보험 자격 | 안다 | 건보 판정만 |
| 근로·사업소득 | 안다 | 1,500만 초과 시 + 건보 |
| 연금수령연차 | 유도 가능 | 한도·감면율 |
| 공적연금 | 대략 안다 | 1,500만 초과 시 + 건보 |
| 금융소득 | 대략 안다 | 1,500만 초과 시 + 건보 |
| 이연퇴직소득 | 퇴직금 액수는 안다 | 세금 |
| 과세제외금액 | 모른다 | 세금 |
| 과세대상 | 모른다 (= 총액 − 위 둘) | 세금 |
| 재산세 과세표준 | 모른다 | 건보 판정만 |

## 3. 해결 전략 — 점진적 공개

처음부터 전부 묻지 않는다. **몰라도 되게 만든다.**

### 3.1 1단계 — 5개만 받고 즉시 결과

```
나이 · 연금 받기 시작한 해 · 계좌 총잔액 · 퇴직금 여부 · 목표 인출액
```

두 가지 설계 판단이 들어 있다.

**연금수령연차를 직접 묻지 않는다.** "받기 시작한 해"에서 계산한다. 아직 안 받았으면 1년차다.

**"퇴직금을 이 계좌로 받으셨나요?"를 1단계에 포함한다.** 예/아니오는 누구나 즉답할 수 있고,
이 하나로 불확실성 대부분이 사라진다.

| 답 | 결과 |
|---|---|
| 아니요 | 잔액 전부가 과세대상으로 **확정** |
| 네 → 금액·근속연수 | **확정** |
| 모르겠어요 | 범위로 표시 |

즉 **대부분의 사용자는 1단계에서 이미 단일 값을 받는다.** 범위는 예외 경로다.

### 3.2 2단계 — 결과 화면 안에서 정확도를 올린다

"입력하세요"가 아니라 **"알려주시면 이만큼 정확해집니다"** 로 제시한다.
질문 목록은 엔진이 반환하는 `missing`에서 생성한다.

### 3.3 3단계 — 조건부 질문

- 목표액이 1,500만 원을 넘는 순간 → 그때 타 소득을 묻는다
- 건강보험 섹션을 펼칠 때 → 그때 자격·재산을 묻는다
- 둘 다 해당 없으면 끝까지 묻지 않는다

### 3.4 "모르겠어요"를 1급 선택지로 둔다

어려운 항목마다 `잘 모르겠어요`를 둔다. 선택하면 **숨기지 않고 결과에 명시**한다.

```
⚠️ 재산세 과세표준을 모르셔서 건강보험 피부양자 판정은 생략했습니다.
   위택스(wetax.go.kr) → 재산세 조회에서 확인하실 수 있습니다.
```

모르는 값을 그럴듯한 기본값으로 덮어 정확한 척하지 않는다.

## 4. 엔진 확장 — `src/lib/tax/range.ts`

기존 `calculateWithdrawal`은 **수정하지 않는다.** 그 위에 래퍼를 얹는다.

미지값을 다루는 판단은 도메인 지식이므로 React 컴포넌트가 아니라 순수 TypeScript에 둔다.
Phase 2 다년도 시뮬레이션에서도 같은 래퍼를 쓴다.

### 4.1 타입

```ts
export type Maybe<T> = T | 'unknown'

export interface PartialWithdrawalInput {
  // 1단계 (필수)
  age: number
  pensionStartYear: number | null   // null = 아직 미수령 → 1년차
  totalBalance: number
  severance: Maybe<{ amount: number; serviceYears: number } | null>  // null = 안 받음
  targetAmount: number

  // 2단계 이후 (조건부)
  taxFree?: Maybe<number>
  otherIncome?: Maybe<OtherIncome>
  healthInsuranceStatus?: Maybe<HealthInsuranceStatus>
  propertyTaxBase?: Maybe<number>
  isLifetimeAnnuity?: boolean
}

export interface Assumption {
  field: string
  reason: string          // "세액공제 한도 초과 납입액이 없다고 가정했습니다"
  impact: 'none' | 'low' | 'high'
  howToConfirm?: string   // "증권사 앱 → 연금계좌 → 과세구분"
}

export interface MissingField {
  field: string
  question: string        // "퇴직금을 이 계좌로 받으셨나요?"
  impact: 'none' | 'low' | 'high'
}

export interface WithdrawalRangeResult {
  certain: boolean                 // true면 min === max
  min: WithdrawalResult            // 가장 유리한 가정
  max: WithdrawalResult            // 가장 불리한 가정
  representative: WithdrawalResult // 화면 대표값
  assumptions: Assumption[]
  missing: MissingField[]
}

export function calculateWithdrawalRange(
  input: PartialWithdrawalInput,
  year?: number,
): WithdrawalRangeResult
```

### 4.2 설계 판단

**대표값은 `max`(보수적)로 둔다.**
세금 계산기에서 낙관적 값을 대표로 보여주면 실제 납부 시 "더 나왔다"가 된다.
반대 방향의 오차가 안전하다.

**미지 범위를 이론적 극단으로 잡지 않는다.**
과세제외금액은 세액공제 한도(연 900만 원)를 초과 납입한 경우에만 생기므로 **기본 0으로 가정**하고,
그 가정을 `assumptions`에 명시한다. 고급 항목에서 직접 입력할 수 있게 둔다.
이론적 극단(전부 비과세)까지 열면 폭만 무의미하게 넓어진다.

**화면 문구를 엔진이 만든다.**
`assumptions`와 `missing`이 화면 문구를 그대로 생성한다. UI가 지어내지 않는다.
가정이 코드 한 곳에만 있고 테스트로 검증된다.

### 4.3 파생 규칙

| 값 | 도출 |
|---|---|
| `pensionYearIndex` | `pensionStartYear === null ? 1 : 현재연도 − pensionStartYear + 1` |
| `balance.deferredSeverance` | `severance.amount` (없으면 0, 미지면 시나리오) |
| `balance.taxFree` | `taxFree` 입력값, 미지면 0 (가정 기록) |
| `balance.taxable` | `totalBalance − taxFree − deferredSeverance` |
| `severanceBasis` | `severance`에서 그대로 |

### 4.4 min / max 산출 규칙

미지 필드가 여러 개일 수 있으므로 정의를 명확히 한다.

- 각 미지 필드가 가질 수 있는 값의 **양 끝(경계값)** 을 후보로 삼는다
- 미지 필드들의 경계값 **조합을 모두 계산**한다
- `min` = 그중 **총세액(`totalTax`)이 가장 작은** 결과
- `max` = 그중 **총세액이 가장 큰** 결과
- 미지 필드가 없으면 조합이 하나뿐이므로 `certain = true`, `min === max`

확정된 값은 그대로 쓰이므로 **답이 쌓일수록 조합 수가 줄고 폭이 좁아진다.**
미지 필드는 최대 4개(`severance`, `taxFree`, `otherIncome`, `propertyTaxBase`)이고
각각 경계값이 2개이므로 조합은 최대 16가지다. 계산 비용은 무시할 수 있다.

## 5. 화면 설계

### 5.1 배치

라우트는 `/` 하나. 위에서 아래로 흐르되 **결과가 항상 보인다.**

```
헤더 — 제목 + "입력하신 정보는 서버로 전송되지 않습니다"
① 기본 입력 (5개)              항상 열림
② 결과                        세금 · 실수령액 · 슬라이더
③ 더 정확하게                 엔진의 missing 기반
④ 상세 리포트                 재원별 차감 · 가정 · 힌트
⑤ 건강보험료 판정              접힘, 펼치면 질문
푸터 — 면책 · 계산 근거 링크
```

**슬라이더 눈금에 `1,500만 원`과 `연금수령한도`를 표시한다.** 세금이 계단식으로 튀는 지점을
직접 만져보게 하는 것이 설명 열 줄보다 낫다.

모바일에서는 ②가 하단 고정 바로 붙어 스크롤해도 세금·실수령액이 보인다.

### 5.2 컴포넌트 경계

상태를 가진 컴포넌트는 하나뿐이다.

```
src/app/page.tsx              서버 컴포넌트 — 정적 소개문·면책(SEO) + <Calculator/>
src/components/calculator/
  Calculator.tsx              'use client'. 유일한 상태 보유자
  BasicInputs.tsx             ┐
  ResultSummary.tsx           │
  RefineQuestions.tsx         ├ props만 받는 순수 표시 컴포넌트
  LedgerTable.tsx             │
  AssumptionList.tsx          │
  HintList.tsx                │
  HealthInsuranceSection.tsx  ┘
```

이렇게 나누는 이유는 Phase 2다. 다년도 화면에서 `LedgerTable`·`AssumptionList`·`HintList`를
연도별로 재사용한다. 상태와 표시를 섞으면 그때 복사·붙여넣기를 하게 된다.

`page.tsx`를 서버 컴포넌트로 남기는 것도 의도적이다. 소개문이 HTML에 포함돼야 검색엔진이 읽는다.

### 5.3 데이터 흐름

```
사용자 입력 → FormState (= PartialWithdrawalInput)
           → useMemo: calculateWithdrawalRange(form)
           → WithdrawalRangeResult
           → 표시 컴포넌트에 props 분배
```

단방향이고 서버 왕복이 없다. 화면 상태 타입과 엔진 입력 타입을 **같은 것**으로 두어
중간 변환 계층을 만들지 않는다.

계산은 순수 함수라 매우 빠르다. **디바운스 없이 매 입력마다 재계산한다.**
슬라이더를 끌 때 숫자가 즉시 따라오는 것이 이 화면의 핵심 경험이므로 지연을 넣지 않는다.

### 5.4 localStorage

- 키 `pension-plan:form:v1`, 변경 후 500ms 디바운스로 저장
- 복원은 마운트 이후 `useEffect`에서 (SSR hydration 불일치 방지)
- **"저장됨 · 지우기"를 화면에 항상 노출한다.** 공용 PC를 쓸 수 있다
- `try/catch`로 감싼다 — 시크릿 모드나 저장 차단 환경에서 예외가 난다

### 5.5 입력 UX 규칙

| 항목 | 방식 |
|---|---|
| 금액 단위 | **만원**으로 입력받고 내부는 원. 사람은 만원 단위로 생각한다 |
| 표시 | 천단위 구분 (`25,000`) |
| 목표 인출액 | 슬라이더 + 숫자 입력 병행. 슬라이더만으로는 정밀 입력이 안 된다 |
| 슬라이더 범위 | 0 ~ 총잔액. 눈금은 `1,500만`·`연금수령한도` |
| 모름 처리 | 어려운 항목마다 `잘 모르겠어요` 라디오 |

### 5.6 에러 처리

| 상황 | 처리 |
|---|---|
| 나이 < 55 | 계산은 하되 "연금수령은 만 55세부터 가능합니다" 경고 배너 |
| 목표액 > 잔액 | 엔진이 반환하는 `shortfall`·경고를 그대로 표시 |
| 잔액 0 / 미입력 | 결과 영역을 계산 대신 안내 문구로 |
| 엔진 예외 | `try/catch`로 감싸 "계산 중 문제가 발생했습니다" + 근거 문서 링크 |

## 6. URL에 입력값을 넣지 않는다

결과 링크 공유는 매력적이지만, 나이·소득·재산이 URL에 들어가면
브라우저 히스토리·리퍼러 헤더·서버 액세스 로그에 남는다.
**ADR 0002(입력값을 서버로 보내지 않는다)와 정면으로 충돌한다.**

재방문 편의는 `localStorage`로 해결한다. 그것은 브라우저 밖으로 나가지 않는다.

## 7. 테스트 전략

도메인 판단을 전부 엔진에 몰아넣었으므로, 테스트할 가치가 있는 곳도 거기에 몰려 있다.

| 대상 | 테스트 | 이유 |
|---|---|---|
| `range.ts` | 철저히 | 로직이 전부 여기 있음 |
| 순수 변환 함수 | 단위 테스트 | 만원↔원, 받기시작한해→연차 |
| 표시 컴포넌트 | 안 함 | props를 JSX로 그리기만 함 |
| 핵심 상호작용 | 3개 | 실제 회귀 위험이 있는 것 |

표시 컴포넌트에 테스트를 붙이지 않는 것은 판단이다. 로직이 없는 곳을 테스트하면
리팩터링할 때마다 깨지기만 하고 버그는 잡지 못한다.

### 7.1 엔진이 보장할 성질 (TDD로 먼저 작성)

1. 답을 추가하면 **폭은 절대 넓어지지 않는다**
2. `certain === true`이면 `min`·`max`·`representative`가 모두 같다
3. 미지 필드가 하나라도 있으면 `assumptions`가 비지 않는다
4. 모든 값이 확정된 입력은 기존 `calculateWithdrawal`과 **결과가 완전히 일치한다**

4번이 회귀 안전망이다. 새 래퍼가 기존 엔진 동작을 바꾸면 즉시 잡힌다.

### 7.2 상호작용 테스트 3개

`@testing-library/react` + `jsdom`을 도입한다.

1. `잘 모르겠어요` → 값 입력 시 범위 표시가 사라지고 단일 값이 된다
2. `localStorage`에 저장된 입력이 재방문 시 복원된다
3. 슬라이더가 1,500만 원을 넘으면 경고가 나타난다

### 7.3 구현 순서

**엔진은 TDD로 간다.** 성질 4개를 테스트로 먼저 쓰고, 실패를 확인한 뒤 구현한다.
Phase 0에서는 구현 후 테스트를 붙였고, 그 결과 틀린 세율을 기대값으로 박은 적이 있다
([TS 0001](../../portfolio/troubleshooting/0001-종신연금-세율-오류.md)).

**UI는 TDD로 가지 않는다.** 레이아웃은 보면서 만드는 것이다. 구현 후 브라우저로 확인한다.

### 7.4 브라우저 확인

단위 테스트로는 레이아웃이 깨진 것을 잡지 못한다.
구현 후 Chrome으로 데스크톱·모바일 뷰포트 스크린샷과 콘솔 에러를 확인한다.

## 8. 완료 기준

```
npm test          전체 통과 (기존 30 + 신규)
npx tsc --noEmit  0 errors
npm run lint      0 errors
npm run build     프로덕션 빌드 성공
```

`npm run build`는 이번이 처음이다. 개발 서버에서 나지 않던 오류가 나올 수 있으므로
배포 전에 반드시 통과시킨다.

그 위에:

- 데스크톱·모바일에서 입력부터 결과까지 동작하고 콘솔 에러가 없다
- 접속 가능한 배포 URL이 있다
- 모든 결과 화면에 면책 문구가 있다
